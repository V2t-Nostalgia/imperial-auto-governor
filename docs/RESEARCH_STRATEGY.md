# 科研战略实验功能

`research_strategy` 默认关闭。它只处理科技选择，不负责经济建设，也不会从 Wiki、论坛或本地原版文件擅自推导“可选科技”。

## 状态来源

`research_profiles.py` 从最新同步存档的玩家国家 `tech_status` 提取：

- 已完成科技及等级；
- 物理、社会、工程三系当前研究、进度和预计完成日期；
- 各领域已经滚出的 alternatives；
- 游戏明确标记的 always available 科技；
- 三系储存研究点和按科技保存的研究点；
- 游戏原生自动科研开关。

当前研究不会进入 `known_technologies`。本地 `common/technology` 只为存档候选补充领域、tier、成本、类别、前置与效果证据，不能创建候选。

## 工具边界

- `inspect_research_state`：返回三系状态和带原版定义证据的合法候选。
- `prepare_research_selection`：只接受对应领域 `legal_candidate_ids` 中的科技。
- `execute_prepared_research`：重新读取存档复核后，通过已启动的会话代理执行命令并等待房主权威确认。

若该领域为空，只执行一次 `062d` 开始研究。若已经有进行中的科技，默认拒绝换题；玩家另行启用中途换题后，执行顺序固定为：

1. `4533` 停止旧科技并等待确认。
2. `062d` 开始新科技并等待确认。
3. 任一步失败后立即停止，账本保留已确认步骤和失败步骤。

当游戏原生自动科研启用时，平台拒绝与其竞争。准备后若当前项目或候选发生变化，也必须基于新存档重新规划。

## 协议状态

Stellaris 4.4.6 的非房主请求与房主回传成对样本表明，开始与停止记录共享相同结构，命令族分别为 `062d01000300` 和 `453301000300`。科技 ID 是带 16 位长度的 ASCII 字段，记录总长度随 ID 变化；房主回传只允许按既有会话代理规则重标记精确匹配的 actor。

解析、动态长度构包、严格目标关联和工具层测试已经通过。新的自主发送执行链仍需下一轮多人实机闭环，因此前端开关默认关闭，本文件不把离线验证描述为生产可用。
