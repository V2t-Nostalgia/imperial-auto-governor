# 会话代理模式

`session_proxy` 是 v0.5.9 的 Windows 推荐执行器。原有 `carrier_click` 作为兼容模式保留，两者可在网页控制台切换；选择会话代理时，载体点击校准和固定点击校验不会显示。

## 工作原理

代理必须在合作玩家加入房间前启动。发现阶段以 WinDivert `SNIFF` 模式被动观察 IPv4 UDP，不阻塞或重注入数据包；它动态枚举本机 `stellaris.exe` 与 Steam 传输进程持有的 UDP 端口，并复用 v0.5.8 的公网/Steam 中继候选规则：进程拥有的端口只需双向流量各出现一次，且至少一个方向具有已验证的可靠传输标记。没有进程归属证据的直连回退仍要求更高包数。填写的房主 IP 是局域网直连提示，不再被误当作公网会话的固定网络对端。

锁定唯一候选后，发现句柄立即关闭，修改句柄只覆盖该实际对端的精确 IPv4 地址与双向端口四元组。随后代理观察当前 command epoch 中的非房主 actor 与 serial。每次动作只在纯 ACK 边界插入一条已经验证的完整应用命令，并为连接余下时间维护：

- 客户端到房主的 sender offset 增量；
- 房主到客户端的 ACK 反向映射；
- 同一合作 actor 后续命令的 serial 增量；
- 与本次目标精确匹配的房主权威广播 actor 重标记。

每次插入的长度按实际命令动态计算，不假定固定 153 字节。等长载体改写仍由旧点击链使用。

### TUN 与全局代理

Wintun、sing-box 等 TUN 路径可能把解封装后的反向 UDP 数据再次标记为 `outbound`。因此会话代理不再把 WinDivert 的方向位作为主要依据，而是先确认本地 Stellaris/Steam 所有的 UDP 端口，再按照已验证四元组的正向或反向排列判定逻辑方向。锁定后的精确过滤器同样匹配两个排列，不要求驱动元数据必须分别标记为 `outbound` 与 `inbound`。

WinDivert priority 只定义多个 WinDivert 句柄之间的先后顺序，不能保证先于其他 WFP 或 TUN 驱动处理。代理因此不通过抢占最高 priority 绕过 TUN。控制台会分别显示“单向可靠”与“双向候选”；只有同一可靠流的两个逻辑方向均出现后才会锁定并允许插入，以免缺少 ACK 反向映射时破坏同步。

### OOS 重新同步

Stellaris 4.4.6 的一次原地 OOS 重新同步样本没有更换 UDP 四元组，也没有重置合作
actor 的 command serial。同步协议自身连续使用了合作端 serial `40` 至 `49`，同步后
两条自然舰船命令继续使用 `50`、`51`。因此代理必须持续观察同步期间的所有非零出站
serial，不能在看到“重新同步”后把下一条命令硬编码为 `1`。

可靠头 byte 5 是每个发送方向独立的 24 位 offset epoch，不是 command serial epoch。
样本中两个方向的该字节分别为 `0` 和 `1`，而 command serial 仍连续递增。详细证据见
[`protocol/OOS_RESYNC_SERIAL_4_4_6.md`](protocol/OOS_RESYNC_SERIAL_4_4_6.md)。

同步状态传输期间不得注入新动作；恢复后应使用同一 actor 最新观察到的所有出站 origin
中的最大非零 serial 加一。只有 UDP 流、玩家槽位或房间会话真正更换时，才应废弃旧流
坐标与 serial 观察并重新学习，不能把原地同步和重新进房混为一谈。

## 已验证动作

- 建筑建设：`b43d`，支持动态长度 `building_*` 标识符。
- 建筑升级与替换：`b43d/c03d` 与 `b43d/bd3d`，槽位和目标建筑均为结构化字段。
- 基础区划建设：`b43d` 内已验证的 district 记录。
- 区域特化：`b43d` 内已验证的 zone 记录。
- 舰队移动：`d32c` 的两个已验证目的地字段形式。
- 星系内坐标移动：`4f2c`，固定长度记录，坐标和当前星系 origin 来自结构化工具输入与最新存档。
- 舰队攻击：`6b33`，来源舰队和敌对目标对象参与精确回包匹配。
- 科研船与工程船自动化：`8f32`，只允许已验证的自动化选项组合。
- 工程船建造恒星基地：`e02c`。
- 殖民：`3d37` 订购殖民船并殖民，以及 `e62c` 使用现成殖民船殖民。
- 恒星基地：`b43d/cb3d` 升级、`b43d/ca3d` 设置模块、`b43d/c93d` 设置建筑；后两者以槽位当前占用状态区分建造和替换。
- 科研选择：`062d` 开始和 `4533` 停止，科技 ID 使用动态长度 ASCII 字段。
- 船坞直接建造：使用已验证的动态舰船设计标识符。
- 舰队编制：`5f3b`/`603b` 逐艘调整 Fleet Manager 目标数量。
- 舰队增援：`123b` 后接 `f23b` 的两阶段请求；必须逐条确认。
- 舰船设计：`fb2d` 克隆并提交一份新设计，不覆盖原设计。

当前目录登记 24 个独立动作。`8f32` 和 `3d37` 的长记录同时验证了超过 255 字节时
`00 00 PP` 应用长度前缀的解析与插入。自动化取消命令 `6836` 的选择字段语义仍未
完全确定，因此本版不构造该命令。

“执行器已验证”只表示结构化目标可以离线构包、插入并与对应房主权威广播精确匹配，
不代表模型可以填写任意对象 ID。经济、科研和舰队 Application 仍需从最新存档建立候选
并通过玩家权限校验。`6b33` 构造器已经接入会话代理，但在敌对目标的确定性存档映射完成
前，舰队 Agent 继续拒绝发包。殖民、舰船自动化和恒星基地动作目前只开放给无 LLM 的
协议兼容性验收，待各自的状态验证器和 Application 工具完成后才会开放自主调用。

`4f2c`、科研、舰船设计与舰队编制增援命令默认关闭，完成当前执行链的多人实机闭环前
仍视为实验功能。

游戏更新后不要逐项临时拼命令验证。使用
[`protocol/PROTOCOL_COMPATIBILITY_SUITE.md`](protocol/PROTOCOL_COMPATIBILITY_SUITE.md)
中的统一验收脚本；命令目录会强制新增代理动作同时提供离线 fixture，并生成可与上一
版本基线比较的 JSON/Markdown 报告。

## 操作顺序

1. Windows Agent 以管理员身份启动。
2. 保持推荐的 `session_proxy`，填写房主 IP 作为直连提示，并确认代理副作用提示。
3. 在合作玩家进入房间之前点击“启动会话代理”，等待 READY。
4. 合作玩家加入房间。若 actor 使用自动识别，本局先自然发出一条合作端命令。
5. 正常运行 Agent。代理可以在同一连接内串行插入多项动作。
6. 先让合作玩家退出多人房间，再点击“停止会话代理”。

控制台在锁定后会显示实际路径类型、实际对端 IP 和双向端口。公网会话显示的实际对端可能是 Steam 中继地址，与玩家填写的房主 IP 不同；这是预期行为。

代理一旦插入过字节，连接两端的可靠流坐标就不再相同。此时在仍连接房间时终止代理会立即破坏同步，因此控制器默认拒绝这种停止请求。

## 失败关闭

代理只接受已登记动作、合法无符号字段、当前 session ID 和纯 ACK 注入边界。公网发现阶段只读取包头和可靠传输标记，不记录 UDP payload；锁定后修改过滤器必须精确到实际流四元组。权威回包必须精确匹配动作对象与来源 actor；超时只记录失败，既不猜测成功，也不撤销已经建立的流坐标映射。任何未知记录都会原样转发。
