# 平台架构

## 1. 目标

平台最终允许一个高能力主总管处理大战略与跨领域取舍，由多个较小的专业 Agent 分别管理经济、舰队、外交或其他领域。主总管不审批每一项廉价动作，而是在低频、高价值节点发布 Mandate、处理升级请求并纠正偏航。

当前有稳定的 `economy_governance` Application，以及默认关闭的实验性 `fleet_operations` 和 `research_strategy` Application。跨星系 `d32c` 舰队移动已经完成真实会话闭环；星系内 `4f2c` 移动、`062d`/`4533` 科研选择、`fb2d` 舰船设计和 Fleet Manager 编制增援已完成存档建模、成对样本解析与离线构包，仍等待当前版本实机闭环后再提升稳定等级。外交等能力仍未实现。

这三个 Application 已各自接入独立的持久模型 Agent。每个 Agent 只加载本领域的角色提示词和工具 schema，并使用独立 SQLite 会话历史与独立 Application 模型路由。专业 Agent 的玩家可见结论和机器审计摘要会汇入战役总账，私有工具协议不会混入经济 Agent 上下文。控制台以全局任务锁串行化它们的副作用；独立模型并不意味着可以同时改写同一条游戏会话。

## 2. 核心对象

### Application

Application 是一个平台原生能力域。它定义可观察状态、专业 Agent 角色、可提交的动作类型和确定性验证规则。Application 必须显式登记在静态注册表中；平台不会扫描并执行未知 Python 插件。

### Content Pack

Content Pack 是声明式适配层。它回答“某个 Stellaris/Mod 对象对应平台已有的什么概念”。它可以声明版本、依赖 Mod、资源映射与提示词补充，但不能新增可执行代码。

判断标准：

- 映射已有建筑、区划、科技或资源：Content Pack。
- 新增平台从未支持的动作或状态：扩展平台/Application。

### Mandate

Mandate 是主总管授予专业 Agent 的完整、不可变授权文件，包含目标、动作白名单、预算、最低储备、权限上限、升级条件与玩家指令。

修改授权时生成一份新的 Mandate，并通过 `supersedes_mandate_id` 指向旧版本。系统不维护可变的 `MandateRevision` 对象，从而让审计时能准确恢复某个决策当时采用的政策。

### Agent Message

专业 Agent 通过结构化消息通信：

- `DomainAssessment`：领域风险与机会。
- `ActionIntent`：等待确定性验证的动作意图。
- `ResourceRequest`：请求调整预算。
- `Escalation`：超出 Mandate 时升级给主总管。
- `ExecutionResult`：执行系统写入的机器事实。
- `PolicyNotice`：通知 Application 切换到新 Mandate。

### Execution Broker

Execution Broker 是未来统一的游戏副作用入口。它负责串行化冲突动作、检查候选与权限、锁定载体、调用 Host Bridge，并把网络或存档证据写入账本。模型文本不能直接把动作标记为成功。

当前 v0.5.9 的 `iag_supervisor.py`、各 Application 的 `agent_tools.py` 和 `SessionProxyController` 已承担其中一部分职责；后续应在保持行为兼容的前提下逐步抽出独立 Broker，而不是重写已验证链路。

### Save Continuation

Save Continuation 是强依赖存档分配字段的持久化状态机。专业 Agent 只提交一次目标、预算与
安全边界；当新存档上传后，平台固定代码提取新 ID、验证唯一性并续接下一阶段，不再为机械
字段解析消耗一次模型回合。每份存档最多执行一个会改变游戏状态的续接动作；发生歧义、
权限变化或校验失败时必须停止。续接动作发出后，当前存档已经过时，不再触发同一份存档的
自主巡检。

## 3. 自主权模型

专业 Agent 在 Mandate 的动作白名单、预算、最低储备与权限上限内自主运行。以下情况必须升级：

- 玩家给主总管的新指令与旧 Mandate 冲突。
- 季度审查发现长期计划偏航。
- 所需动作超出权限或预算。
- 状态证据过旧、互相冲突或不足以安全执行。
- 多个 Application 对同一资源或对象提出冲突请求。

主总管的价值在于偶尔做昂贵但影响深远的决策，而不是成为每个建设按钮的同步审批器。

## 4. 调度与上下文

第一版的策略判断仍只支持玩家配置的周期巡检。存档上传事件可以唤醒确定性 Save
Continuation，但不能自行引入新的策略判断；其他游戏事件驱动调度仍要等对应数据能够稳定
提取后再引入。

每场战役拥有独立会话、战略要求、十年计划、紧急状态和执行账本。模型上下文可以压缩，但结构化 Mandate、玩家配置、机器执行事实和未完成动作不得只存在于自然语言摘要中。

每个专业 Agent 还拥有与战役绑定的私有对话库。玩家可从网页会话栏直接向某个领域发消息或触发该领域巡检；周期自主巡检则依次运行已启用的科研、舰队和经济 Agent，并在全部领域结束后只安排一次下一轮检查。

## 5. 启动验证

平台启动时至少检查：

1. 当前游戏版本是否在 Content Pack 支持范围内。
2. 所需 Mod 是否存在并启用。
3. Mod 版本是否在已验证范围内。
4. Content Pack manifest 与映射 schema 是否有效。
5. Content Pack 声明的平台能力是否已经注册。

第一版不要求复杂签名或沙箱系统，但校验失败必须显式阻止对应 Content Pack 生效。

## 6. 配置归属

巡检频率、模型选择、温度、上下文上限、压缩阈值、预算、最低储备、权限等级和高风险确认策略都属于玩家配置。代码可以给出保守默认值，但不能把这些政策永久写死在专业 Agent 内部。

## 7. 网络安全边界

执行层同时保留两种边界：

- `carrier_click` 只替换已识别的 Stellaris 协作载体命令，并保持长度、方向和确认约束。
- `session_proxy` 在进房前以只读 SNIFF 阶段复用 Stellaris/Steam 进程端口归属来发现直连或公网中继流；锁定后把修改范围收窄到实际四元组，只在纯 ACK 边界插入已验证的应用记录，并在整个连接余下时间维护可靠流坐标与 actor serial。它必须在进房前启动、离房后停止。

未知包不应改写。任何扩大协议覆盖面的工作都必须先留存样本、做差分实验、解析语义，再接入执行器。舰队 `d32c` 移动已通过真实会话闭环；`4f2c`、科研 `062d`/`4533`、舰船设计 `fb2d` 和 Fleet Manager 编制增援当前保持默认关闭，等待新执行链的实机闭环。`6b33` 攻击构造器和权威回包匹配已经进入会话代理，但舰队 Application 在确定性敌对目标映射完成前仍会拒绝发包。殖民、民用舰船自动化和恒星基地命令同样先进入无 LLM 协议验收，不能把“执行器可构包”误写成“模型可提交任意 ID”。

## 8. 模型供应商边界

Application 只依赖稳定的模型消息入口，不直接操作 HTTP。基础设施层把 Responses / Chat Completions 协议与 `openai_sdk` / `raw_http` 传输分开：官方异步 SDK 是默认实现，原始 HTTP 是玩家显式选择的兼容路径。

一个逻辑模型池包含多个玩家配置的端点。运行时按优先级使用端点，并以结构化 HTTP 错误、连接状态和 `Retry-After` 维护进程内冷却。401/403、404、429 与明确未得到响应的连接错误可以换端点；5xx、超时和未知错误不得自动重放。端点探测是只读观测，不得擅自改变持久化配置。
