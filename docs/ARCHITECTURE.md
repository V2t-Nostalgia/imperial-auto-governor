# 平台架构

## 1. 目标

平台最终允许一个高能力主总管处理大战略与跨领域取舍，由多个较小的专业 Agent 分别管理经济、舰队、外交或其他领域。主总管不审批每一项廉价动作，而是在低频、高价值节点发布 Mandate、处理升级请求并纠正偏航。

当前有稳定的 `economy_governance` Application，以及默认关闭的实验性 `fleet_operations` 和 `research_strategy` Application。跨星系 `d32c` 舰队移动已经完成真实会话闭环；星系内 `4f2c` 移动、`062d`/`4533` 科研选择、完整多区段 `fb2d` 舰船设计和 Fleet Manager 编制增援已完成存档建模、成对样本解析与离线构包，仍等待当前版本实机闭环后再提升稳定等级。外交等能力仍未实现。

这三个 Application 已各自接入独立的持久模型 Agent。每个 Agent 只加载本领域的角色提示词和工具 schema，并使用独立 SQLite 会话历史。模型路由由玩家逐 Application 配置：可以独立选择模型池和逻辑模型，也可以显式沿用经济治理当前的模型路由与请求参数；后者不会合并角色提示词、工具、Application 设置或私有历史。网页端把每个 Application 呈现为独立联系人，其玩家消息、自主报告和工具摘要只写入所属聊天线程；跨领域信息只通过显式联合复盘和结构化执行账本协调。控制台以全局任务锁串行化它们的副作用；独立模型并不意味着可以同时改写同一条游戏会话。

## 2. 核心对象

### Application

Application 是一个平台原生能力域。它定义可观察状态、专业 Agent 角色、可提交的动作类型和确定性验证规则。Application 必须显式登记在静态注册表中；平台不会扫描并执行未知 Python 插件。

### Content Pack

Content Pack 是声明式适配层。它回答“某个 Stellaris/Mod 对象对应平台已有的什么概念”。它可以声明版本、依赖 Mod、资源映射与提示词补充，但不能新增可执行代码。

判断标准：

- 映射已有建筑、区划、科技或资源：Content Pack。
- 新增平台从未支持的动作或状态：扩展平台/Application。

### Mandate

Mandate 是主总管授予专业 Agent 的完整、不可变授权文件，包含目标、动作白名单、预算、最低储备、权限上限、升级条件与玩家指令。

修改授权时生成一份新的 Mandate，并通过 `supersedes_mandate_id` 指向旧版本。系统不维护可变的 `MandateRevision` 对象，从而让审计时能准确恢复某个决策当时采用的政策。

### Agent Message

专业 Agent 通过结构化消息通信：

- `DomainAssessment`：领域风险与机会。
- `ActionIntent`：等待确定性验证的动作意图。
- `ResourceRequest`：请求调整预算。
- `Escalation`：超出 Mandate 时升级给主总管。
- `ExecutionResult`：执行系统写入的机器事实。
- `PolicyNotice`：通知 Application 切换到新 Mandate。

### Execution Broker

Execution Broker 是未来统一的游戏副作用入口。它负责串行化冲突动作、检查候选与权限、锁定载体、调用 Host Bridge，并把网络或存档证据写入账本。模型文本不能直接把动作标记为成功。

当前 v0.5.10 的 `iag_supervisor.py`、各 Application 的 `agent_tools.py` 和 `SessionProxyController` 已承担其中一部分职责；后续应在保持行为兼容的前提下逐步抽出独立 Broker，而不是重写已验证链路。

### Resource Reservation Ledger

控制台任务锁负责进程内副作用串行化；`ResourceReservationLedger` 进一步处理“多个
Application 依次读取同一份旧存档，却各自认为库存仍完整”的逻辑竞态。它把预留写入
战役 SQLite，并用 `BEGIN IMMEDIATE` 原子检查同一存档哈希下的余额。已知费用可在余额
范围内并存，未知动态费用独占该存档的支出资格；新存档哈希会废止全部旧预留。

### Application Plan Book

经济、舰队和科研分别维护一本活动计划书。计划是可执行的分层目标图，而不是自然语言
报告或固定动作队列：节点可以声明父目标、依赖、激活条件、模型制定的容差、停止和完成
条件，并只在参数已经确定时附加一个 `prepare_*` 及可选 `execute_*` 动作。条件引用各领域
读取工具产生的稳定事实路径；列表对象以 fleet、planet、technology 等持久 ID 编址，避免
数组顺序变化造成伪异常。

`ApplicationPlanBook` 每次只读取计划实际监视的事实。容差内变化直接由固定程序推进；
异常从直接受影响节点沿父子和依赖边传播，局部修改不能删除完成节点，也不能在失效前提下
声称保留其依赖者。创建、补丁前后快照、保留／撤销范围、工具结果、暂定执行和新存档确认
均写入审计；新活动计划不能覆盖旧活动计划，已结束计划在替换前归档。

### Exception Adviser And Joint Review

可选快速参谋使用独立模型配置，只接收已定位异常、相关事实和局部计划。其输出被限制为
继续当前观测值、修改受影响分支，或把压缩后的问题升级给领域主模型。范围验证会拒绝它
改写无关或已完成节点；没有配置、响应无效或超时时直接回退给领域主模型。局部主模型回合
同样不加载完整会话历史、全局事实或完整计划。

低频联合审查默认每 12 个游戏月读取各领域计划的有界摘要和计划已经监视的事实。审查者
只能向目标 Application 的收件箱投递局部复查指令，不能直接修改计划。目标领域在自己的
下一次运行中决定是否以及如何修改，从而保持计划所有权边界。

### Save Continuation

Save Continuation 是强依赖存档分配字段的持久化状态机。专业 Agent 只提交一次目标、预算与
安全边界；当新存档上传后，平台固定代码提取新 ID、验证唯一性并续接下一阶段，不再为机械
字段解析消耗一次模型回合。每份存档最多执行一个会改变游戏状态的续接动作；发生歧义、
权限变化或校验失败时必须停止。续接动作发出后，当前存档已经过时，不再触发同一份存档的
自主巡检。

## 3. 自主权模型

专业 Agent 在 Mandate 的动作白名单、预算、最低储备与权限上限内自主运行。以下情况必须升级：

- 玩家给主总管的新指令与旧 Mandate 冲突。
- 年度或按玩家配置周期运行的联合审查发现长期计划偏航。
- 所需动作超出权限或预算。
- 状态证据过旧、互相冲突或不足以安全执行。
- 多个 Application 对同一资源或对象提出冲突请求。

主总管的价值在于偶尔做昂贵但影响深远的决策，而不是成为每个建设按钮的同步审批器。

## 4. 调度与上下文

第一版的策略判断仍只支持玩家配置的周期巡检。存档上传事件可以唤醒确定性 Save
Continuation，但不能自行引入新的策略判断；其他游戏事件驱动调度仍要等对应数据能够稳定
提取后再引入。

每场战役拥有独立会话、战略要求、十年计划、紧急状态和执行账本。模型上下文可以压缩，但结构化 Mandate、玩家配置、机器执行事实和未完成动作不得只存在于自然语言摘要中。

每个专业 Agent 还拥有与战役绑定的私有对话库。网页端的联系人、模型 Context 和持久 Thread 一一对应；玩家当前打开的联系人就是普通消息的唯一目标，后台自主消息也回到所属 Thread。时间只影响联系人最近活动、预览和未读状态，不会把不同领域重新合并为全局时间线。玩家可直接向某个领域发消息或触发该领域巡检；周期自主巡检并发启动已启用的科研、舰队和经济 Agent，使一个领域的慢模型不会阻止其他领域开始检查。

自主轮次开始时，`WorldStateService` 以存档路径、大小、mtime、SHA-256、战役 ID 和上传 revision 固定一个不可混用的 `WorldSnapshot`。同轮所有 Agent 接收同一个对象；新上传只能供下一轮使用。快照内的 `WorldStateIndex` 以 Future single-flight 复用公共 Clausewitz 区段和数字对象表，派生的经济、科研、舰船、舰队、入侵、扩张和 `CampaignRoutePlanner` 也按参数缓存。CPU 密集的冷状态按依赖顺序只构建一次；之后最多 4 个线程在共享内存上运行互不依赖的 inspect、候选和路径读取。这里刻意不用 Windows `multiprocessing` 搬运完整 gamestate。默认只保留一个热快照；旧轮次仍持有自己的只读引用，不会被新存档污染。

只读池对每批任务设置统一墙钟 deadline。超时任务返回自己的结构化工具错误，已完成的兄弟任务仍保留；发生超时后整代 daemon worker 被退役，下一批使用新 generation，避免一次永久阻塞耗尽服务。读取和推理可以并行，但任何 `prepare_*`、`execute_*`、审计型状态动作和共享资源预留都不进入该池，而是经过同一个可重入执行锁及 SQLite 事务串行完成。确定性 Plan 还在 prepare 和 execute 前各检查一次快照新鲜度。全部领域结束后只安排一次下一轮检查，并在到期时运行一次联合审查。

构造提供商消息时，会话库只回放连续且完整的 assistant `tool_calls`／对应 tool 结果组。
孤立、缺失、重复或中断的工具结果仍保留在本地数据库和审计界面，但被隔离在模型协议
上下文之外；专业 Application 的工具审计保留在自己的私有库中，不会伪装成另一个
Application 的 tool 结果。联合审查只读取有界计划摘要和明确允许的结构化事实。

## 5. 启动验证

平台启动时至少检查：

1. 当前游戏版本是否在 Content Pack 支持范围内。
2. 所需 Mod 是否存在并启用。
3. Mod 版本是否在已验证范围内。
4. Content Pack manifest 与映射 schema 是否有效。
5. Content Pack 声明的平台能力是否已经注册。

第一版不要求复杂签名或沙箱系统，但校验失败必须显式阻止对应 Content Pack 生效。

## 6. 配置归属

巡检频率、模型选择、温度、上下文上限、压缩阈值、预算、最低储备、权限等级和高风险确认策略都属于玩家配置。代码可以给出保守默认值，但不能把这些政策永久写死在专业 Agent 内部。

## 7. 网络安全边界

执行层同时保留两种边界：

- `carrier_click` 只替换已识别的 Stellaris 协作载体命令，并保持长度、方向和确认约束。
- `session_proxy` 在进房前以只读 SNIFF 阶段复用 Stellaris/Steam 进程端口归属来发现直连或公网中继流；锁定后把修改范围收窄到实际四元组，只在纯 ACK 边界插入已验证的应用记录，并在整个连接余下时间维护可靠流坐标与 actor serial。它必须在进房前启动、离房后停止。

未知包不应改写。任何扩大协议覆盖面的工作都必须先留存样本、做差分实验、解析语义，再接入执行器。舰队 `d32c` 移动已通过真实会话闭环；`4f2c`、科研 `062d`/`4533`、舰船设计 `fb2d` 和 Fleet Manager 编制增援当前保持默认关闭，等待新执行链的实机闭环。`fb2d` 的模型输入不是裸封包：舰队 Application 只允许从玩家已有设计出发，并按需暴露本机规则与已研究科技证明合法的区段、槽位和组件。`6b33` 攻击、`8f32` 民用船自动化、`e02c` 工程船建站、`3d37` 自动殖民和恒星基地操作已经接入存档候选与 Application 权限层，模型只能选择候选而不能提交任意对象 ID。现成殖民船 `e62c` 与自动化取消 `6836` 仍因字段语义未闭合而不向 Agent 开放。

## 8. 模型供应商边界

Application 只依赖稳定的模型消息入口，不直接操作 HTTP。基础设施层把 Responses、Chat Completions 与 Anthropic Messages 协议同 `openai_sdk`、`anthropic_sdk` 和 `raw_http` 传输分开。两个官方异步 SDK 承担常规路径，原始 HTTP 是玩家显式选择的特殊兼容路径。

一个逻辑模型池包含多个玩家配置的端点。运行时按优先级使用端点，并以结构化 HTTP 错误、连接状态和 `Retry-After` 维护进程内冷却。401/403、404、429 与明确未得到响应的连接错误可以换端点；5xx、超时和未知错误不得自动重放。端点探测是只读观测，不得擅自改变持久化配置。
