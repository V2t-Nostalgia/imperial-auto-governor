# Stellaris 4.4.6 Fleet Manager 编制与增援记录

本文件记录一次获授权合作模式差分实验的可复现结论，不包含会话地址、端口、完整抓包
或用户路径。原始 PCAPNG 的 SHA-256 为：

`9BA12A86F459CD85619C66A3B90CE3AEF541F595044FC5A76F63774A43404F3E`

## 实验顺序

第一舰队执行 `+1`、`-1`、连续三次 `+1`、点击“增援全部”；随后创建第二舰队，
对第二舰队执行同样操作。两个舰队使用同一份玩家设计 `3188`。第一舰队模板 ID 为
`0`，房主为新模板分配的第二舰队模板 ID 为 `175`。

客户端动作 serial 为 `46..60`：

| serial | 动作 |
|---:|---|
| 46 | 第一舰队 `+1` |
| 47 | 第一舰队 `-1` |
| 48–50 | 第一舰队连续三次 `+1` |
| 51–52 | 第一舰队旧版“增援全部”混合会话中的两条记录 |
| 53 | 创建第二舰队模板 |
| 54 | 第二舰队 `+1` |
| 55 | 第二舰队 `-1` |
| 56–58 | 第二舰队连续三次 `+1` |
| 59–60 | 第二舰队旧版“增援全部”混合会话中的两条记录 |

房主按相同顺序回传 actor/origin 已重标记的权威记录，房主 serial 为 `89..103`。

## 命令族

| 命令族 | 长度 | 已确认语义 |
|---|---:|---|
| `5f3b01000300` | 153 | 指定 Fleet Manager 模板与设计的目标数量 `+1` |
| `603b01000300` | 143 | 指定 Fleet Manager 模板与设计的目标数量 `-1` |
| `123b01000300` | 94 | 对当前选中舰队请求增援 |
| `f23b01000300` | 94 | 旧混合样本中的全帝国／其他增援路径，精确语义未闭合 |
| `7e3b01000300` | 91 | 请求创建一份空 Fleet Manager 模板 |

关键字段标签：

| 标签 | 代码中的中性名称 |
|---|---|
| `0e3b01001400` | `fleet_template_id` |
| `652c01001400` | `design_id` |
| `143501001400` | `upgrade_id` |
| `c84401000c00` | `growth_stage` |
| `822c01001400` | `context_822c` |

`+1` 记录包含 `context_822c`，`-1` 记录不包含。创建模板的请求中没有房主随后分配的
模板 ID；这意味着不能从单条 `7e3b` 记录读取结果 ID，但不等于不能执行创建流程。

## 选中舰队增援复核

后续用舰队详情面板的“补充舰队”按钮做了独立干净抓包。PCAPNG 的 SHA-256 为：

`A1E785564936CE893E27FF3C4AF95E8B68F7A317A389EC7D0272ED60A2120FDD`

该抓包只出现一条 `123b01000300`，没有任何 `f23b01000300`。记录中的
`0e3b01001400` 精确指向所选 Fleet Manager 模板，非房主请求与房主权威回传可配对。
因此公开执行器把“选中舰队增援”定义为单条 `123b`；不会再根据旧混合样本自动追加
`f23b`。后者只保留为尚未解析的证据，等待单独的全帝国增援差分实验。

## 四次连续创建补充实验

第二次被动实验连续执行四组“创建空模板，然后对同一设计 `+1`”。脱敏 PCAPNG 的
SHA-256 为：

`0D87D276E965FE354B67405A09610762CF98E2107C606BC044DFA2646673FED1`

| 组 | 客户端创建 serial | 房主创建 serial | 随后的模板 ID | 客户端 `+1` serial | 房主 `+1` serial |
|---:|---:|---:|---:|---:|---:|
| 1 | 62 | 105 | 177 | 63 | 106 |
| 2 | 64 | 107 | 178 | 65 | 108 |
| 3 | 66 | 109 | 179 | 67 | 110 |
| 4 | 68 | 111 | 180 | 69 | 112 |

八个创建包都由 28 字节可靠流头和一条 91 字节 `7e3b` 记录组成。去除 serial 后，八条
记录逐字节相同。三条房主 UDP datagram 在创建记录后还合并了独立的 21 字节状态节拍，
其中同样没有 177–180。由此可确认：模板 ID 是双方执行权威创建命令时由确定性对象
分配器产生，不是隐藏在创建记录或相邻回包里。

同一 command epoch 内连续分配是 `+1`，但这不能升级成“永远用上一 ID 加一”的规则：
两次实验之间已经出现未在该抓包中分配的 176。平台因此发送真实 `7e3b`，随后等待一份
新存档，从玩家拥有的模板集合差分中唯一确认新 ID；若同时出现多个新模板则停止，不猜。

## 执行规则

Fleet Manager 没有在该样本中发送“把数量设为 N”的绝对命令。把目标从 1 调整为 4
必须发送三条 `5f3b`，每条使用独立 serial 并分别等待房主确认。只有全部目标增量确认
后，才发送一条 `123b`。任一步失败都停止后续动作。

存档是舰队 ID、模板 ID、设计 ID、实际数量、目标数量和已有增援队列的唯一事实来源。
网络确认只证明目标编制修改和增援请求被房主接受，不证明任何舰船已经完成建造。

## 验证等级

- 两支舰队的非房主请求与房主权威回传：已有完整配对。
- 四组连续模板创建与后续 `+1`：已有完整配对。
- 四个公开命令族的离线精确 fixture 和 parse/build 往返：已通过；`f23b` 不进入公开动作目录。
- 存档模板、设计、实际/目标数量和逐舰队权限校验：已通过。
- `session_proxy` 已接入模板创建、存档差分解析和后续定量增援状态机；完整从零建舰多人
  实机闭环仍待下一轮测试。
