# Stellaris 4.4.6 舰队维修与升级记录

本文件记录获授权合作模式实验中，军用舰队“返港维修”和“升级舰队”的非房主请求、
房主权威回传及同步存档交叉验证。公开仓库只保存结构结论和脱敏 fixture，不包含会话
地址、端口或完整抓包。

该记录与民用船自动化共享外层 `8f32` 命令族，但内部对象和固定标志不同。记录只包含
来源舰队，没有显式恒星基地、星系或船坞队列目标。游戏依据当前状态选择返港目的地，
执行器不得擅自塞入额外目标字段。

Agent 候选要求最新存档确认舰队属于玩家、当前空闲、未失踪、未交战，并且按单舰最大值
归一化后的船体、装甲或护盾聚合能够证明存在损伤。网络确认只证明返港命令成立；维修
进度和完成状态仍由后续存档确认。

| 第二目标 `c33d` | 3 |
| 第二 PCAPNG SHA-256 | `D8678E5CB8C5ED504AE33233E6EC05FC7D5DE4E7DE2B97985B99E871AD6E7BC1` |

同步存档确认：第一目标恒星基地索引为 105、所在星系为 217，而其
`shipyard_build_queue=9167`；第二座船坞的对应队列为 3。对第一座基地执行普通跨星系
移动时，移动命令使用恒星基地索引 105，而升级命令继续使用 `c33d=9167`。因此 `c33d`
不是星系 ID、恒星基地索引或 station 对象，而是目标恒星基地的船坞建设队列 ID。

升级候选必须从最新存档提取己方带 `shipyard` 模块的恒星基地及其
`shipyard_build_queue`，并要求至少一艘舰船的
`ship_design_implementation.upgrade` 不是 `0xffffffff`。准备和执行阶段都会重新验证
舰队与队列；模型不能自行填写任意对象 ID。

## 验证状态

- 两个命令族都有字节精确的离线 fixture、parse/build 往返和回包目标匹配测试。
- 会话代理动作目录分别登记 `repair_fleet` 与 `upgrade_fleet`。
- 网页控制台提供独立总开关，并对每支舰队分别保存维修和升级权限。
- 最终舰船耐久、设计和队列变化仍以新存档为准。
