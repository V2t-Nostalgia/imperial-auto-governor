# Stellaris 4.4.6 陆军招募命令

2026-09-12 的非房主合作端样本确认，Stellaris 4.4 在恒星基地“进攻部队中心”界面
招募陆军时使用 `b43d01000300` 命令族。虽然入口位于恒星基地，底层建设对象仍关联
该星系殖民地的全局 `type=army` 队列。

## 完整配对

| 项目 | 客户端请求 | 房主权威广播 |
|---|---:|---:|
| actor | 2 | 2 |
| origin | 0 | 0 |
| serial | 28 | 49 |
| 记录长度 | 152 | 152 |

两条记录仅在偏移 58 的 serial 低字节不同；清零 serial 后逐字节完全相同。PktMon
记录 966 个数据包且无丢失。应用前缀为 `000000`，完整应用增量为 155 字节。

## 已确认字段

| 偏移 | 标签或值 | 样本值 | 含义 |
|---:|---|---:|---|
| `70..75` | `822c01001400` | 0 | 中性命令上下文 |
| `80..85` | `634001001400` | 1 | 陆军建设队列 ID |
| `90..95` | `c83d01000300` | - | 陆军设计容器 |
| `96..101` | `ec4601000f00` | - | 陆军脚本 ID 字符串标签 |
| `102..103` | u16 | 12 | ASCII 字符串长度 |
| `104..115` | ASCII | `robotic_army` | 招募的陆军类型 |
| `116..121` | `4c2b01001400` | 182 | 招募物种 ID |
| `126..131` | `132a01001400` | 0 | 来源殖民地的 colony 对象 |
| `136..141` | `0c3a01001400` | 0 | 招募界面所在的恒星基地管理器条目 |
| `146..151` | `040004000400` | - | 稳定尾部 |

第一次样本中 `132a` 与阿拉尔主恒星 ID 恰好同为 0，不能据此沿用舰队移动命令中的
标签语义。后续 Ctrl 样本把来源改为另一殖民地：陆军队列 8686 的 location 是
`planet=7516`，而该行星保存 `colony=114`；对应请求恰好为 `132a=114`。因此 `132a`
在 `b43d` 上下文中已经确认是来源 colony 对象。`0c3a` 在两次使用同一招募空间站时
均为 0，与阿拉尔 `starbase=0` 一致。

## 队列与界面映射

同步存档中的相关对象为：

| 对象 | ID | 类型或位置 |
|---|---:|---|
| 阿拉尔殖民地 | planet 4 | owner 0，system 2 |
| 陆军建设队列 | queue 1 | owner 0，`type=army`，location type 2 / id 4 |
| 恒星基地建设队列 | queue 2 | `type=starbase`，location starbase 0 |
| 舰船建设队列 | queue 3 | `type=ships`，location starbase 0 |

因此 `6340=1` 不能从恒星基地对象的 `build_queue` 或 `shipyard_build_queue` 直接读取。
固定程序应在全局建设队列中查找 owner、`type=army` 与对应殖民地 location 三者匹配
的唯一队列。旧版存档若在行星上直接保存 `army_build_queue`，可以作为经过版本判断的
兼容来源，但不得优先覆盖 4.4 的实际全局队列关系。

## Ctrl 批量招募

在同一恒星基地界面按住 Ctrl 点击一次招募项后，会话代理观察到：

| 方向 | serial | 数量 | 记录长度 |
|---|---|---:|---:|
| 客户端请求 | `29..33` | 5 | 每条 152 字节 |
| 房主广播 | `50..54` | 5 | 每条 152 字节 |

因此 Ctrl 没有专用协议，也没有在单条记录中编码数量 5。它只是由客户端连续产生五条
普通 `b43d`。PktMon 完整保留了客户端 serial `30..33` 的正文；四条记录除 serial 外
逐字节相同，且每条连同三字节应用前缀占用 155 个可靠流字节。serial 29 及五条房主
正文未被 NIC 层完整保留，但会话代理在路径上观察到全部十条同长度命令。

这次四条完整请求使用 `queue=8686`、`robotic_army`、species 182、`colony=114` 和
`starbase=0`。同步存档确认 queue 8686 是 owner 0 的 `type=army` 队列，location 指向
planet 7516，而 planet 7516 的 colony 对象正是 114。这也构成 `132a` 语义的第二组
差分证据。

执行器若向模型提供 `count`，应在一个行动锁内把它展开为 N 条各自分配 serial 的普通
命令，并逐条接受房主确认。不得构造一个带虚拟数量字段的 `b43d`；任一条失败后应停止
余下批次，并按已确认数量结算资源与待存档审计状态。

## 自动化边界

接入执行器时应由固定程序生成候选并校验：

1. 恒星基地仍由玩家控制，且其所在星系存在可用进攻部队中心；
2. `6340` 指向玩家拥有、location 对应该殖民地且 `type=army` 的队列；
3. `ec46` 陆军脚本在当前游戏与 Content Pack 中存在，并允许所选物种招募；
4. `4c2b` 物种仍受玩家控制，且资源、队列容量和陆军上限允许本次招募；
5. `132a` 从队列 location 对应行星的 colony 对象确定，`0c3a` 从招募空间站确定，
   模型不得直接填写对象 ID；
6. 房主确认后等待新存档核对队列项，不以本地界面动画作为最终成功依据。

本样本验证了 `robotic_army`。其他陆军类型可按同一长度前缀 ASCII 字段建模，但只有
当前规则层实际枚举为可招募的脚本 ID 才能进入候选；不得仅凭名称猜测 DLC 或 Mod 陆军。
